# Настройки и дополнительные команды

## Команды и режимы

Для локального запуска: `node --env-file=.env dist/cli.js <команда> [флаги]`.
Для отдельного запуска в Compose: `docker compose run --rm beget-acme <команда> [флаги]`.
Не запускайте второй процесс выпуска или очистки параллельно с постоянным сервисом.

| Команда                       | Поведение                                                                                                          |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `run`                         | Выпускает отсутствующий сертификат или продлевает при необходимости, затем продолжает работу; команда по умолчанию |
| `run --once`                  | Выпускает или продлевает при необходимости, завершает очистку DNS и выходит                                        |
| `schedule`                    | Автоматически продлевает существующий production-сертификат; не выполняет первоначальный выпуск                    |
| `schedule --once`             | При необходимости продлевает существующий production-сертификат, завершает очистку DNS и выходит                   |
| `issue [staging\|production]` | Однократный выпуск или продление при необходимости; по умолчанию staging                                           |
| `renew [staging\|production]` | Однократное продление существующего сертификата при необходимости; по умолчанию production                         |
| `status`                      | Только чтение: сроки сертификатов, восстановление и блокировка                                                     |
| `doctor`, `probe`             | Только чтение: диагностика Beget и DNS; две формы одной команды                                                    |
| `setup`                       | Проверяет DNS и сохраняет разрешение локально; не меняет DNS и не создаёт ACME-заказ                               |
| `cleanup`                     | Удаляет принадлежащие журналу DNS-записи и обновляет журнал с исходной конфигурацией                               |
| `journal-clear`               | Аварийно архивирует журнал после проверок пустоты DNS и ручного подтверждения                                      |
| `init`                        | Создаёт шаблон `.env`, не перезаписывая существующий файл                                                          |
| `help`                        | Показывает общую справку без выполнения операции                                                                   |

`run` и `schedule` включают восстановление перед выпуском и планирование повторов.
`issue` и `renew` не запускают этот цикл: незавершённый DNS-журнал нужно предварительно
обработать через `cleanup` с исходной конфигурацией. Для них, как и для `cleanup`, нужна
разрешённая конфигурация. `issue` не является принудительным перевыпуском: подходящий
действующий сертификат вне окна продления сохраняется.

### Флаги и окружение

- `--once` — только `run` и `schedule`. Один полный цикл, включая необходимый выпуск/продление,
  ожидание DNS, CA и очистку. Если обновление не нужно — нового заказа нет. После успеха
  или ошибки процесс выходит, не начинает следующий цикл. Ошибка даёт ненулевой код.
  Сохранённая задержка после ошибки соблюдается: до её окончания возвращается
  `RENEW_RETRY_DEFERRED`, без ожидания или досрочного выпуска. Обычная пауза после успеха
  не мешает запуску `--once`: срок сертификата проверяется сразу после восстановления.
- `--staging` — `run`, `setup`, `status`, `doctor`, `probe`, `cleanup`, `journal-clear`.
  Без него эти команды используют `ACME_ENVIRONMENT`, по умолчанию production.
  `schedule` всегда использует production. Для `issue` и `renew` задавайте окружение
  позиционно, например `issue staging` или `renew production`.
- `--accept-dns-replacement` — `run`, `schedule`, `setup`; подтверждает проверку выделенных
  DNS-имён в панели. В `run`/`schedule` альтернативой служит `ACME_ACCEPT_DNS_REPLACEMENT=yes`.
  Отдельный `setup` запрашивает интерактивное подтверждение либо требует флаг без терминала.
- `--dry-run` — только `issue`: проверка DNS без аккаунта ACME, заказа и записи DNS.
  Разрешённая конфигурация требуется и в этом режиме. Пример: `issue staging --dry-run`.
- `--check` — только `status`: ненулевой код, если выбранное окружение не готово.
- `--json` — формат событий журнала для всех команд; ошибки пишутся в stderr.
  Вывод справки и версии остаётся обычным текстом.
- `--help` / `-h` — общая справка; `--version` / `-V` — версия. Оба завершают вызов без
  выполнения операции; настройки и учётные данные не нужны.

Флаги могут стоять до или после команды. Полная таблица также доступна в
[README](../../README.md#команды-и-справка) и через `node dist/cli.js --help`.

### Аварийное архивирование журнала

`journal-clear` не удаляет DNS-записи и не заменяет `cleanup`. Используйте её только после
ручной проверки панели и разбора неоднозначного результата. Укажите все имена текущего
журнала через запятую в `ACME_CONFIRM_JOURNAL_CLEAR` и причину проверки длиной не менее
10 символов в `ACME_JOURNAL_CLEAR_REASON`. Приложение проверяет пустоту имён и стабильность
ответов настроенных authoritative DNS перед архивированием журнала. Подробности —
[неоднозначное восстановление](OPERATIONS.md#диагностика-и-неоднозначное-восстановление).

## Основные параметры

| Переменная                          | Значение                                                                 |
| ----------------------------------- | ------------------------------------------------------------------------ |
| `ACME_DOMAINS`                      | Точный список SAN через запятую, максимум 100                            |
| `ACME_EMAIL`                        | Контактная почта ACME                                                    |
| `BEGET_USERNAME`, `BEGET_PASSWORD`  | Учётные данные API Beget                                                 |
| `ACME_ENVIRONMENT`                  | `production` по умолчанию; `staging` для тестового сервиса               |
| `BEGET_ZONES`                       | Необязательный список управляемых зон вместо автоматического определения |
| `ACME_STATE_DIR`, `ACME_OUTPUT_DIR` | Пути приложения; по умолчанию `./state`, `./output`                      |
| `STATE_DIR`, `CERTIFICATES_DIR`     | Пути хоста в Compose; внутри контейнера всегда `/state`, `/output`       |
| `APP_UID`, `APP_GID`                | Пользователь Compose, по умолчанию `10001:10001`                         |

`setup` сохраняет разрешение отдельно для staging и production. Подтверждение связано
с доменами, выбранными зонами, серверами, логином. Пароль не сохраняется
в setup-файле; его смена не требует повторного подтверждения DNS. Изменение каталога
сертификатов требует прав доступа, но не нового DNS-разрешения.

## Секреты

Вместо прямых значений поддерживаются `BEGET_USERNAME_FILE` и `BEGET_PASSWORD_FILE`.
Не задавайте одновременно значение и файл одного секрета. Начальный UTF-8 BOM и конечные
переводы строк удаляются; пробелы сохраняются. В `.env` значения с `#` заключайте в кавычки.

Для Compose есть [пример secrets](../../examples/compose.secrets.yml). Удалите прямые
credentials из `.env`, создайте `secrets/username.txt` и `secrets/password.txt`, ограничьте
доступ и разрешите чтение выбранному UID/GID. Запускайте Compose с двумя файлами:

```sh
docker compose -f docker-compose.yml -f examples/compose.secrets.yml run --rm beget-acme setup
```

Используйте ту же пару файлов при `up`, `run` и остальных командах. Compose secrets с
локальными файлами не заменяют защиту файлов и резервных копий на хосте.

## Дополнительные настройки

| Переменная                  | По умолчанию         | Назначение                                    |
| --------------------------- | -------------------- | --------------------------------------------- |
| `BEGET_NAMESERVERS`         | Четыре сервера Beget | Проверяемые authoritative DNS                 |
| `ACME_PUBLIC_RESOLVERS`     | `1.1.1.1,9.9.9.9`    | Recursive DNS; им видны запрашиваемые имена   |
| `ACME_DNS_TIMEOUT_MS`       | `900000`             | Таймаут ожидания одного DNS-имени             |
| `ACME_CLEANUP_SETTLE_MS`    | `45000`              | Непрерывное отсутствие TXT после удаления     |
| `ACME_RENEW_BEFORE_DAYS`    | не задано            | Треть срока или явный порог дней              |
| `ACME_RETRY_INTERVAL_MS`    | `3600000`            | Интервал после ошибки, 60000–86400000 мс      |
| `ACME_SCHEDULE_INTERVAL_MS` | `43200000`           | Пауза между успешными проверками              |
| `ACME_PRIVATE_KEY_MODE`     | `0600`               | Допустимо `0640` для настроенной общей группы |

Таймаут должен превышать интервал стабильности очистки более чем на 30 секунд.
Синхронизируйте часы хоста. Настройка CNAME-делегирования не поддерживается.

## Планировщик

Один последовательный цикл: после успеха проверка через ACME_SCHEDULE_INTERVAL_MS
(12 часов), после любой операционной ошибки — через ACME_RETRY_INTERVAL_MS (1 час).
Retry-After CA может увеличить задержку. Лимита попыток нет. Режим и время следующей
проверки сохраняются между перезапусками. Перед новым выпуском выполняется безопасная
очистка журнала; чужие записи и неоднозначные мутации не обходятся. Ошибка восстановления
оставляет сервис работающим и ожидающим следующей попытки. С `--once` сервис выполняет
необходимый выпуск/продление и очистку за один цикл, затем выходит. При ошибке или ещё
не наступившем сроке повтора возвращает ненулевой код внешнему планировщику.
ACME_RENEW_BEFORE_DAYS не задана — порог треть фактического срока; задана — ровно указанное
число дней. Продление начинается, когда оставшийся срок меньше порога. Явный порог больше
срока сертификата приведёт к продлению при каждой обычной проверке: выбирайте его осознанно.

## Совместимость TLS для ACME

ACME использует встроенный HTTPS-транспорт Node с TLS 1.2–1.3. При таймауте
установления соединения (10 секунд), сбросе или некоторых ошибках согласования
до завершения рукопожатия выполняется один повтор с ограничением TLS 1.2.
Обе попытки разделяют общий таймаут запроса и сигнал остановки. Проверка сертификата
сервера остаётся обязательной. Ошибки сертификата, DNS, ответы HTTP и сбои после
рукопожатия не вызывают этот повтор. Beget продолжает использовать прежний транспорт.
Предупреждение о fallback не доказывает, что причиной сбоя была TLS 1.3.

После успешного fallback на TLS 1.2 выбор сохраняется по хосту ACME в `state/tls/`
на 7 дней, включая перезапуски. `ACME_TLS_FALLBACK_TTL_MS` меняет срок
(по умолчанию 604800000 мс; диапазон 60000–31536000000 мс). Обычные запросы через 1.2
не продлевают TTL. После истечения следующий реальный запрос снова разрешает TLS 1.2–1.3.
Новый успешный fallback запускает новый TTL; неудачный — нет. Фоновых проверок нет.
Старые файлы без времени сохранения считаются истёкшими. Уменьшение настройки сокращает
и срок существующих предпочтений; время из будущего игнорируется. Для ручного сброса
остановите сервис и удалите файл соответствующего хоста из `state/tls/`.
Staging и production имеют разные хосты и отдельные предпочтения.
DNS-проверки используют ровно список BEGET_NAMESERVERS (по умолчанию четыре сервера
.com и .pro), а не все возможные NS Beget. Для расширения списка задайте его явно и
повторите setup после завершения recovery. В cleanup повторяются чтения DNS, а не удаления.

## Запуск без отдельного setup

run и schedule принимают --accept-dns-replacement или ACME_ACCEPT_DNS_REPLACEMENT=yes.
Значение по умолчанию — разрешение не задано. Флаг/env явно подтверждает замену записей
вычисленных DNS-имён и ручную проверку панели. При отсутствии подходящего разрешения
первоначальная настройка выполняется внутри запуска: права, зоны, пустота DNS и журнал.
Подходящее разрешение используется повторно без повторения setup. Повреждённый файл
разрешения не перезаписывается автоматически. Незавершённое восстановление блокирует
изменение области разрешения. Сохранённый setup без флага по-прежнему поддерживается.
Для первого выпуска используйте run; schedule требует существующий production-сертификат.

Диагностика только для чтения доступна при отсутствующем, изменённом или повреждённом setup;
команды записи сохраняют проверки разрешения. `status --check` считает такое разрешение
неисправным. JSON-события ошибок содержат отдельные поля `code` и необязательное `hint`.
