# Beget ACME

Выпуск и автоматическое продление сертификатов Let's Encrypt через DNS API Beget.
Один экземпляр обслуживает один сертификат с точным списком SAN: домены, поддомены и wildcard.
Проект beta. [English](docs/en/README.md) · [Настройки](docs/ru/CONFIGURATION.md) · [Безопасность](SECURITY.md)

## Минимальная конфигурация

Создайте .env из .env.example и заполните:

```dotenv
BEGET_USERNAME=your_api_login
BEGET_PASSWORD=your_api_password
ACME_EMAIL=admin@example.com
ACME_DOMAINS=example.com,*.example.com,api.example.com
```

Wildcard не включает базовое имя. Для IDN используйте punycode. Зоны определяются через
API Beget; BEGET_ZONES позволяет задать их явно. CNAME-делегирование не поддерживается.

Beget заменяет все записи конкретного DNS-имени. Перед первым запуском проверьте в панели,
что вычисленные _acme-challenge имена пусты и выделены
этому приложению. Флаг --accept-dns-replacement означает ваше согласие с такой заменой,
включая ручную проверку панели, если API не предоставляет перечень записей.

## Локальный запуск одной командой

Используйте Node.js из .node-version, затем npm ci и npm run check для установки и сборки.
Отдельная команда setup необязательна:

```sh
node --env-file=.env dist/cli.js run --staging --once --accept-dns-replacement
```

После проверки staging запустите production:

```sh
node --env-file=.env dist/cli.js run --accept-dns-replacement
```

run автоматически выполнит первоначальные проверки и сохранит разрешение, выпустит
отсутствующий сертификат и затем будет проверять продление каждые 12 часов. --once делает
одну проверку и завершает работу. Для сохранённого подходящего разрешения флаг не нужен.
Альтернатива флагу — ACME_ACCEPT_DNS_REPLACEMENT=yes в .env; разрешение распространяется
на окружение команды, поэтому не включайте его для production до осознанного решения.

setup остаётся отдельной необязательной командой предварительной проверки с интерактивным
CONFIRM. Она не меняет DNS и не создаёт ACME-заказы. schedule также допускает inline setup
через флаг/env, но сохраняет прежний смысл: продление уже существующего production-сертификата.
Для первого выпуска используйте run.

## Docker Compose

Для сборки из исходников выполните docker compose build. Добавьте в .env:

```dotenv
ACME_ACCEPT_DNS_REPLACEMENT=yes
STATE_DIR=./state
CERTIFICATES_DIR=./output
APP_UID=10001
APP_GID=10001
```

До запуска создайте каталоги и дайте выбранному UID/GID доступ. Пример Linux:

```sh
mkdir -p state output
sudo chown 10001:10001 state output
sudo chmod 700 state
sudo chmod 750 output
```

При своих путях и UID/GID замените значения. На Windows используйте ACL. Для Docker
rootless учитывайте отображение UID на хосте: процесс без root и rootless daemon — разные
настройки. Compose не создаёт отсутствующие bind-каталоги автоматически.

Тест одной командой:

```sh
docker compose run --rm beget-acme run --staging --once
```

Production-сервис после успешной проверки:

```sh
docker compose up -d
docker compose logs -f
```

Контейнер работает без root, с read-only rootfs, без Docker socket и повышения привилегий.
Для секретов из файлов предусмотрен [Compose overlay](examples/compose.secrets.yml).
После публикации задайте BEGET_ACME_IMAGE, выполните docker compose pull и запускайте

## Результат и диагностика

Сертификаты: output/production/current/fullchain.pem и privkey.pem; для staging отдельный
каталог staging. При собственном пути замените output. Монтируйте в TLS-сервер весь каталог
сертификатов read-only, чтобы current разрешался корректно. Reload настраивается отдельно.
Ключ по умолчанию 0600; опциональный ACME_PRIVATE_KEY_MODE=0640 требует общей группы и
подходящих прав каталогов. [Пример Nginx](examples/nginx.conf).

```sh
node --env-file=.env dist/cli.js status --staging --check
node --env-file=.env dist/cli.js doctor --staging
```

status --check проверяет сертификат выбранного окружения и состояние восстановления,
а не доступность веб-сервера. Пока первый сертификат не выпущен, healthcheck неуспешен.

Все настроенные NS и recursive-резолверы должны видеть TXT, после чего сразу начинается
проверка CA. Очистка проверяет только authoritative NS Beget и ждёт 45 секунд устойчивого
отсутствия записей. Кэши публичных резолверов не задерживают очистку. Повторяются чтения DNS.

Один последовательный цикл: после успеха проверка через ACME_SCHEDULE_INTERVAL_MS
(12 часов), после любой операционной ошибки — через ACME_RETRY_INTERVAL_MS (1 час).
Retry-After CA может увеличить задержку. Лимита попыток нет. Режим и время следующей
проверки сохраняются между перезапусками. Перед новым выпуском выполняется безопасная
очистка журнала; чужие записи и неоднозначные мутации не обходятся. Ошибка восстановления
оставляет сервис работающим и ожидающим следующей попытки. --once делает одну попытку
и возвращает ошибку внешнему планировщику, включая ещё не наступившее время повтора.
ACME_RENEW_BEFORE_DAYS не задана — порог треть фактического срока; задана — ровно указанное
число дней. Продление начинается, когда оставшийся срок меньше порога. Явный порог больше
срока сертификата приведёт к продлению при каждой обычной проверке: выбирайте его осознанно.
Успешный TLS 1.2 fallback запоминается по хосту CA в state/tls/.

## Состояние, восстановление и обновления

Сохраняйте state и output при обновлениях; там находятся ключи, разрешения, журнал и
счётчики повторов. Перед сменой доменов, NS или логина остановите сервис и завершите
recovery со старой конфигурацией. Новый scope требует setup или явного флага/env inline setup.
Нельзя одновременно запускать несколько клиентов для одних challenge-имён.
При ошибке проверьте status/doctor, затем cleanup с прежней конфигурацией и --staging
для staging. Не удаляйте журнал для обхода ошибки. [Восстановление](SECURITY.md).

Состояние храните на локальной файловой системе, не SMB/NFS. Системная блокировка
освобождается при гибели процесса. Восстановление запускается до ожидания следующего
выпуска, сохраняя ограничения CA. Подробнее — [восстановление](docs/ru/OPERATIONS.md#восстановление-после-остановки).
